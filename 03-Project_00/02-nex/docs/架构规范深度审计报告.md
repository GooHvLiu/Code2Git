## 二、前端问题清单

### 🔴 高优先级问题（影响架构规范一致性）

#### 问题 F-001：Layout 目录大写开头

| 项目 | 内容 |
|------|------|
| **当前路径** | `src/Layout/` |
| **问题描述** | 目录名使用大写开头 `Layout`，与其他目录（全小写）命名风格不一致 |
| **涉及文件** | `Layout/index.vue`、`Layout/AppMain.vue`、`Layout/Navbar.vue`、`Layout/Sidebar.vue`、`Layout/SidebarItem.vue`、`Layout/TagsView.vue`、`Layout/TagMenus.vue` |

| **影响范围** | 需要修改所有引用该目录的 import 语句（router、main.js 等） |

| 项目 | 内容 |
|------|------|
| **当前路径** | `src/utils/` |
| **问题描述** | 28 个 JS 文件直接放在 utils 目录下，没有按功能分类子目录，文件数量过多不利于维护 |

## 六、架构规范建议

### 6.1 目录命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 前端目录 | 全小写，多单词用连字符 | `src/layout/`、`src/project-config/` |
| 后端目录 | 全小写，多单词用连字符 | `src/modules/i18n-manager/` |
| 前端组件目录 | PascalCase | `components/TranslateProgressDialog/` |

### 6.2 文件命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| Vue 组件 | PascalCase 或 index.vue | `UserDialog.vue`、`index.vue` |
| JS 工具函数 | camelCase | `request.js`、`auth.js` |
| 后端 controller | `模块名.controller.js` | `user.controller.js` |
| 后端 service | `模块名.service.js` | `user.service.js` |
| 后端 route | `模块名.route.js` | `user.route.js` |
| 后端 model | `模块名.model.js` | `user.model.js` |
| 后端 schema | `模块名.schema.js` | `user.schema.js` |
| 后端中间件 | `名称.middleware.js` | `auth.middleware.js` |
| 后端配置 | `名称.config.js` | `app.config.js` |
| 测试文件 | `名称.test.js` | `user.controller.test.js` |

### 6.3 模块结构规范

**后端标准模块结构**：

## 七、总结

### 7.1 整体评价

项目整体架构规范度较高，前后端都采用了成熟的架构模式：
- 前端基于 vue-element-admin，目录划分清晰
- 后端采用模块化架构，23 个业务模块职责明确
- 路由自动扫描、分层设计、中间件抽象都符合大厂规范

### 7.2 主要问题

1. **命名风格不统一**：前后端模块命名、部分文件命名存在不一致
2. **文件分类不清晰**：前端 utils 目录文件过多，后端 email 模块包含非核心文件
3. **部分模块结构不完整**：user、notification、license 等模块结构需要确认
4. **重复代码**：super-panel 和 system 下存在重复组件

### 7.3 建议执行顺序

1. **先确认后修改**：对于结构不完整的模块（user、notification、license），先确认业务逻辑，再决定是否修改
2. **先低风险后高风险**：先修改命名不统一等低风险问题，再修改 utils 分类等高风险问题
3. **分阶段提交**：每个阶段完成后提交一次 Git，便于回滚
4. **充分测试**：每次修改后运行构建和主要功能测试
