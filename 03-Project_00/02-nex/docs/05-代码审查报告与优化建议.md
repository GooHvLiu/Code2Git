## 二、已修复问题

### 🔴 BUG-001：request.js 中 PARAM_INVALID 处理块重复（已修复）

**严重级别**：严重
**文件**：`前端/src/utils/request.js`（原第 214-253 行）

**问题描述**：
响应拦截器中存在两个完全独立的 `if (res.code === 'PARAM_INVALID')` 处理块。第一个块（214-228行）会始终匹配并 `return Promise.reject(res)`，导致第二个块（231-253行）成为**永远不会执行的死代码**。

第一个块的国际化 key 查找逻辑将 type 中的点号替换为下划线（如 `string.min` → `string_min`），与 i18n 语言包中的 key 格式一致；第二个块则直接使用带点号的 key（`error.PARAM_INVALID.password.string.min`），vue-i18n 会将点号解析为嵌套对象，导致查找失败。

**修复方案**：
合并为一个处理块，保留第一个块的下划线转换逻辑，同时采用第二个块的多级降级查找策略（field.type → type → default → 原始消息）。

**修复后代码**：
```javascript
if (res.code === 'PARAM_INVALID') {
  const i18nInvalid = require('@/i18n').default
  const { field, type, message: rawMessage } = res.data || {}
  const typeKey = (type || '').replace(/\./g, '_')
  let paramMessage
  // 1. 优先 field.typeKey
  if (field && type && i18nInvalid.te('error.PARAM_INVALID.' + field + '.' + typeKey)) {
    paramMessage = i18nInvalid.t('error.PARAM_INVALID.' + field + '.' + typeKey, res.data || {})
  }
  // 2. 其次 typeKey
  else if (type && i18nInvalid.te('error.PARAM_INVALID.' + typeKey)) {
    paramMessage = i18nInvalid.t('error.PARAM_INVALID.' + typeKey, res.data || {})
  }
  // 3. 通用兜底
  else if (i18nInvalid.te('error.PARAM_INVALID.default')) {
    paramMessage = i18nInvalid.t('error.PARAM_INVALID.default', res.data || {})
  }
  // 4. 原始消息兜底
  else {
    paramMessage = rawMessage || res.msg || '参数错误'
  }
  showError(paramMessage)
  return Promise.reject(res)
}
```

## 三、Bug 与逻辑错误

### 🟠 BUG-002：后端错误响应不设置 HTTP 状态码

**严重级别**：高
**文件**：`后端/src/middleware/error.middleware.js`

**问题描述**：
`errorHandler` 中间件对所有错误（包括业务错误、参数错误、数据库错误、系统错误）都使用 `res.json()` 返回，**未设置 HTTP 状态码**，默认全部返回 200。这导致：
- 前端无法通过 HTTP 状态码区分错误类型
- 监控系统（如 Sentry、APM）无法正确统计错误率
- 不符合 RESTful API 设计规范

**建议**：
```javascript
// 业务错误返回 200（业务码在 body 中），但系统错误应设置对应状态码
if (err instanceof BusinessError) {
  return res.status(200).json({...});
}
if (err.name === 'ValidationError') {
  return res.status(400).json({...});  // 参数错误 400
}
if (err.code && err.code.startsWith('ER_')) {
  return res.status(500).json({...});  // 数据库错误 500
}
// 未知错误 500
return res.status(500).json({...});
```

### 🟡 BUG-003：config.service.getConfigValue 每次都触发全量查询

**严重级别**：中
**文件**：`后端/src/modules/config/config.service.js` 第 92-95 行

**问题描述**：
`getConfigValue(key)` 内部调用 `getAllConfigs()`，而 `getAllConfigs()` 有 60 秒缓存。但 `getConfigValue` 没有单独的缓存机制，如果在一次请求中多次调用不同 key，每次都会检查缓存（虽然缓存命中时不查数据库，但仍有对象拷贝开销）。更重要的是，`updateConfigs` 后调用 `clearCache()`，但如果在缓存有效期内有其他服务直接修改了数据库（如数据库管理功能），缓存不会失效。

**建议**：
- 考虑使用 `getConfigsByCategory` 减少数据量
- 数据库管理功能修改配置表后应主动调用 `configService.clearCache()`
- 或引入基于版本号的缓存失效机制

### 🟡 BUG-004：菜单版本号比较使用字符串时间可能精度丢失

**严重级别**：中
**文件**：`后端/src/modules/menu/menu.model.js` 第 96-101 行

**问题描述**：
`findUserMenuTreeWithVersion` 中使用 `new Date(version).getTime() === new Date(currentTime).getTime()` 比较版本号。如果 MySQL 的 `update_time` 精度为秒级（DATETIME 默认秒级），同一秒内的多次修改可能导致版本号相同，前端不会刷新菜单。

**建议**：
- 将 `update_time` 改为 `DATETIME(3)` 毫秒级精度
- 或使用自增版本号字段替代时间戳比较

### 🟢 BUG-005：router.js 日志打印与实际路径不一致

**严重级别**：低
**文件**：`后端/routes/router.js` 第 35-36 行

**问题描述**：
实际挂载路径为 `/prod-api/v2/${moduleName}`，但 console.log 打印的是 `/api/${moduleName}`，误导开发调试。

**建议**：统一日志输出为实际路径。

## 五、性能优化建议

### 🟡 PERF-001：前端请求重试可能导致重复写入

**严重级别**：中
**文件**：`前端/src/utils/request.js` 第 280-295 行

**问题描述**：
请求重试机制对**所有**网络错误和 5xx 错误进行重试，包括 POST/PUT/DELETE 请求。如果后端已处理请求但响应超时，重试会导致**重复写入**（如重复创建用户、重复下单）。

**建议**：
```javascript
// 仅对 GET 请求和幂等请求自动重试
const shouldRetry = reqConfig.retry !== false &&
  reqConfig.method === 'get' &&  // 增加方法判断
  (!error.response || RETRY_CONFIG.retryableStatus.includes(error.response.status))
```
或在后端为写操作添加幂等键（Idempotency-Key）。

### 🟡 PERF-002：数据库查询缺少分页优化

**严重级别**：中
**涉及模块**：audit, notification, email-log 等

**问题描述**：
审计日志、通知、邮件日志等表数据量会随时间快速增长，但查询接口的分页使用 `LIMIT offset, size`，在 offset 较大时性能较差。同时部分查询缺少时间范围默认限制。

**建议**：
- 对大表使用**游标分页**（基于 id/create_time 的 WHERE 条件）替代 offset 分页
- 列表查询默认限制时间范围（如最近 30 天）
- 确保常用查询字段有索引（已基本覆盖）

### 🟢 PERF-003：前端 i18n 语言包体积过大

**严重级别**：低
**问题描述**：
zh-CN.js 约 2583 行，en-US.js 约 2550 行，全部打包进主 bundle。其中 27% 为未使用键。

**建议**：
- 清理未使用键后体积可减少约 25%
- 考虑按模块动态加载语言包（`import()` 异步加载）
- 使用 `@intlify/unplugin-vue-i18n` 的资源压缩

### 🟢 PERF-004：配置服务缓存粒度较粗

**严重级别**：低
**文件**：`后端/src/modules/config/config.service.js`

**问题描述**：
`getAllConfigs()` 将所有 47 个配置项全部加载到内存缓存，每次获取单个配置值都返回全量对象的浅拷贝。

**建议**：
- 当前数据量小（47项），性能影响可忽略
- 未来配置项增多时，可考虑按 category 分组缓存

### 🟢 PERF-005：前端路由切换取消请求机制可优化

**严重级别**：低
**文件**：`前端/src/utils/request.js` 第 39-78 行

**问题描述**：
`pendingMap` 使用 `method-url` 作为 key，相同 URL 的并发请求会互相取消。在某些场景（如同时发起多个相同 URL 的不同参数请求）可能导致意外取消。

**建议**：
将 key 改为 `method-url-params` 或使用请求唯一 ID（UUID）。

## 六、安全风险

### 🟠 SEC-001：.env 文件包含敏感信息且存在默认弱密码

**严重级别**：高
**文件**：`后端/.env`

**问题描述**：
- `.env` 文件包含数据库密码（默认 `123456`）、JWT 密钥、邮箱授权码等敏感信息
- 数据库默认密码 `123456` 为弱密码，生产环境存在安全风险
- 需确认 `.env` 已在 `.gitignore` 中排除（当前项目中 .env 存在于工作目录）

**建议**：
1. 确认 `.gitignore` 包含 `.env`
2. 生产环境使用强密码（至少 16 位，包含大小写字母、数字、特殊字符）
3. JWT 密钥使用随机生成的 64 位以上字符串
4. 考虑使用 Vault、AWS Secrets Manager 等密钥管理服务

### 🟠 SEC-002：SQL 备份文件中文注释乱码

**严重级别**：高
**文件**：`后端/backups/database/full_2026-09-05T10-25-33-274Z.sql`

**问题描述**：
数据库备份文件中的中文 COMMENT 全部显示为乱码（mojibake），表明备份时客户端字符集设置不正确。虽然不影响数据本身，但：
- 备份文件可读性差，影响灾难恢复时的理解
- 可能暗示数据库连接字符集配置存在问题
- 如果恢复到不同字符集的数据库可能导致数据损坏

**建议**：
- 备份时使用 `--default-character-set=utf8mb4` 参数
- 检查 `mysqldump` 命令的字符集配置
- 验证备份文件可正确恢复

### 🟡 SEC-003：CORS 配置过于宽松

**严重级别**：中
**文件**：`后端/app.js` 第 39 行

**问题描述**：
`app.use(cors())` 使用默认配置，允许**所有来源**的跨域请求。对于企业级内部系统，应限制允许的来源。

**建议**：
```javascript
const corsOptions = {
  origin: process.env.ALLOWED_ORIGINS?.split(',') || ['http://localhost:8082'],
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'DELETE', 'PATCH']
}
app.use(cors(corsOptions))
```

### 🟢 SEC-004：用户密码重置 Token 未设置使用次数限制

**严重级别**：低
**文件**：`后端/src/modules/user/`

**问题描述**：
`nex_password_reset_token` 表记录了重置 Token，但未看到针对同一用户的 Token 生成频率限制和并发 Token 数量限制。

**建议**：

- Token 有效期建议不超过 15 分钟

## 七、可维护性问题

### 🟠 MAIN-001：PLC 配置双轨制可能导致不一致

**严重级别**：高
**涉及文件**：`后端/.env`、`后端/src/modules/config/config.model.js`

**问题描述**：
PLC 连接参数（协议、主机、端口、单元ID、轮询间隔）同时存在于：
1. **环境变量**（`.env` 中的 `PLC_PROTOCOL`, `PLC_HOST`, `PLC_PORT` 等）
2. **数据库配置表**（`nex_system_config` 中的 `plcProtocol`, `plcHost`, `plcPort` 等）

两套配置的优先级和同步机制不明确。数据库配置支持在线修改，但环境变量需要重启服务。如果运维人员修改了环境变量但忘记更新数据库（或反之），会导致配置不一致。

**建议**：
- 明确数据库配置为**运行时唯一真相源**，环境变量仅作为首次启动的默认值
- 系统启动时将环境变量写入数据库（仅当数据库中不存在时）
- 在文档中明确配置优先级

### 🟡 MAIN-002：后端模块命名不一致

**严重级别**：中
**涉及目录**：`后端/src/modules/`

**问题描述**：
模块目录命名风格不统一：
- `device-part`（kebab-case）
- `feature-config`（kebab-case）
- `db-manager`（kebab-case）
- `file-manager`（kebab-case）
- `i18n-manager`（kebab-case）
- `project-config`（kebab-case）
- 其他模块如 `user`, `role`, `menu`, `config`（单词）

虽然 kebab-case 是合理的命名规范，但与简单单词模块混用时不够统一。

**建议**：全部使用 kebab-case（如 `device-part`）或全部使用简单单词，保持一致。

### 🟡 MAIN-003：前端 API 层缺少统一的类型定义

**严重级别**：中
**问题描述**：
前端 API 层（`src/api/*.js`）的请求参数和响应数据缺少 TypeScript 类型定义或 JSDoc 注释，开发时无法获得智能提示，容易传错参数。

**建议**：
- 为每个 API 函数添加 JSDoc 注释（参数类型、返回值、错误码）
- 或逐步迁移到 TypeScript
- 使用 OpenAPI/Swagger 自动生成类型定义（后端已有 swagger-jsdoc）

### 🟡 MAIN-004：后端缺少单元测试

**严重级别**：中
**问题描述**：
`package.json` 中声明了 `jest` 开发依赖，`test/` 目录存在，但实际测试覆盖情况不明。核心业务逻辑（如认证、权限、PLC 通信、审计）缺少自动化测试。

**建议**：
- 优先为核心业务逻辑（认证、权限校验、配置管理）编写单元测试
- 为关键 API 编写集成测试
- 在 CI 中运行测试并设置覆盖率门槛

### 🟡 MAIN-005：前端缺少错误边界和全局异常处理

**严重级别**：中
**问题描述**：
前端有 `errorLog` store 模块和错误日志页面，但缺少 Vue 的 `errorHandler` 全局异常捕获和 React 风格的 Error Boundary。组件渲染异常可能导致白屏。

**建议**：
```javascript
// main.js 中添加
Vue.config.errorHandler = (err, vm, info) => {
  store.dispatch('errorLog/addErrorLog', { err, vm, info })
  // 生产环境可上报到监控平台
}
```

### 🟡 MAIN-006：后端路由自动扫描缺少错误隔离

**严重级别**：中
**文件**：`后端/routes/router.js`

**问题描述**：
`loadAllRoutes()` 遍历 modules 目录加载路由，如果某个模块的路由文件有语法错误或依赖缺失，会导致**整个服务启动失败**，且错误信息不够明确。

**建议**：
```javascript
try {
  const moduleRouter = require(routePath);
  router.use(`/prod-api/v2/${moduleName}`, moduleRouter);
} catch (err) {
  console.error(`❌ 路由加载失败 [${moduleName}]:`, err.message);
  // 不中断启动，记录错误
}
```

## 九、代码亮点

在审查过程中也发现了不少值得肯定的设计：

1. **自动扫描路由**：`router.js` 自动扫描模块目录，新增模块零配置注册，扩展性好
2. **菜单版本缓存**：通过 `MAX(update_time)` 版本号机制减少菜单接口的数据传输
3. **多级错误降级**：前端 PARAM_INVALID 处理支持 field.type → type → default → 原始消息的四级降级
4. **审计哈希链**：`nex_audit_log` 表使用 `prev_hash`/`current_hash` 实现防篡改哈希链，满足 GMP 合规
5. **配置自动补全**：`config.model.initDefaultData()` 只插入缺失的配置项，升级时自动补全新参数，不覆盖已有值
6. **请求取消机制**：前端 `pendingMap` 支持路由切换时取消未完成请求，避免内存泄漏
7. **内置角色国际化**：内置角色名称使用 i18n key，自定义角色使用数据库值，兼顾灵活性和国际化
8. **Beehive 授权**：集成了完整的授权验证机制，包括时间守卫、白名单、自动时间校准
